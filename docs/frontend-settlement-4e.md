# 4-E 모의 정산·작업 이벤트 안내

## 근거·설계

기능명세서 SETTLE-01(50행), WORK-04(70행), P16/P19/P22와 D12, 계획 4단계 3·4항을 따른다. 기술 PDF의 React/Router/Query/Axios/Zod와 기존 MSW 구조·KEMI 토큰을 유지한다. API 문서와 API/shared에는 정산/작업 사건 계약이 없어 DEV 전용 `/__mock__/settlements`로 분리한다. 실제 지급/외부 제공자/DB 검증은 아니다.

## 구현 계획·완료 조건

1. `mocks/settlement-model.ts`, `settlement-handlers.ts`: 계약·성공 결제의 금액/통화, 준비/보류, 승인→최종 전달→전용 수령 연결을 검사한다. 10% 공제/의뢰인 별도 0%와 금액 합계를 검사하고 계약당 성공 기록 하나만 생성한다. 단위 검사로 불충분 조건·중복·내용 충돌·실패/결과 미확정을 확인한다.
2. `features/resolution/SettlementSummary.tsx`, `mocks/SettlementMock.tsx`, `settlement-api.ts`: 실제 보호 라우트에 연결하고 기존 영상/준비/작업방에서 진입한다. 양측이 동일 결과를 조회하며 사용자 금액/완료 판정 입력은 받지 않는다. 조회 오류 시 과거 완료를 숨기고 같은 요청 재시도/재조회로 복구한다.
3. `SettlementNoticesMock.tsx`: 확정된 성공 기록에서만 같은 방 시스템 안내와 정확한 계약/정산 ID 링크를 파생한다. 기존 영상/요청/최종 안내를 보존하고 서명/준비 사건도 저장된 기록에서 조회한다. 인앱 알림 생성/읽음은 별도 7단계다.
4. 데스크톱/모바일에서 공개 모집→양측 서명→전액 Mock 결제→준비/제작→검토/승인→최종 전달→수령→모의 정산 통합 및 양측·비당사자·비회원·실패/지연·운영 Mock 제외를 검사한다. 기존 4단계 연관 검사를 실행하고 결과/제한을 진행 문서에 기록한다. 검사/검토 후 의미 단위 커밋·푸시·Draft PR로 전달한다.

## 실패 대비·정책 경계

- 성공 기록 전에는 완료 표시/성공 시스템 안내를 만들지 않는다. 중복 처리·동시 요청은 최신 Map 값을 본문/지연 이후 읽고 계약당 성공 기록 하나로 귀결한다. 응답 유실은 저장과 구분하며 재조회/같은 ID 재시도로 확인한다.
- 수수료 10%는 확정이지만 D12 VAT/절사는 미결정이다. 10으로 나누어떨어지는 원화 계약만 이 예시에서 계산하며 소수 원 수수료는 정책 확인 대기로 차단한다. 세금 0원으로 확정하거나 임의 반올림하지 않는다.
- 취소·분쟁·환불 실제 상태 계약은 미제공이다. 기존 준비/파일 문제와 개발용 보류 fixture를 반영한다. 실제 보류 해제·취소·부분 환불은 이번에 구현하지 않으며 운영 무보류 판정 증거로 사용하지 않는다.
- 명령 실행 권한/처리 시점은 최종 API 계약이 아니다. 양측의 결과 확인 요청이 Mock 처리기를 호출하며 처리기가 조건을 검사한다. 버튼/URL/클라이언트 금액으로 성공하지 않는다.
- 단일 탭 메모리·새로고침 초기화, 다중 탭/영구 복원/실제 권한·동시성은 미검증이다. 시스템 안내는 확정 원기록에서 파생하여 중복 없이 재조회한다. 안내 조회 실패로 거래 기록을 취소하지 않는다.
- 4단계 정상 Mock 통합과 단계 전체 완료를 구분한다. WORK-02·D09/D10/D11/D12/D13/D17/D20 및 실제 API/스토리지는 남으며 4단계 전체 완료로 표시하지 않는다.
