# 4-A 준비·제작 시작·납기

기준: 기능명세 READY-01/02(39~40행), WORK-01/02(41~42행), P11/P12, D09/D10. 계획 §4단계 첫 항목까지만 구현한다. API 문서 및 현재 API/shared에는 준비·납기 계약이 없다.

## 구현 순서·검증 기준

1. `src/mocks/production-model.ts`와 단위 검사: 구조화 준비 조건 양측 확인, 발송/제공/정상 확인 분리, 결제·서명 게이트, 1회 시작, 정정·멱등·버전 충돌, 양측 납기 변경을 검증한다.
2. `production-handlers.ts`, `production-api.ts`, `ProductionMock.tsx`, `features/production/ReadinessPanel.tsx`, `DeadlineChangePanel.tsx`: 기존 서명/결제 저장본을 조회하고 본인 당사자만 허용한다. 작업 방/결제에서 준비 화면을 연결한다. API는 DEV MSW `/__mock__/production/:contractId`다.
3. Playwright로 기존 공개 제안→조건/양측 서명→결제→준비→시작→문제 정정→변경 승인 흐름과 오류·권한을 검사한다. 운영 빌드 Mock 제외와 관련 회귀를 확인하고 진행 기록·Draft PR로 전달한다.

## 미결정·Mock 경계

- 조건서의 자료/기간은 자유 텍스트다. 자동 해석하지 않는다. 의뢰인이 필수 제품/파일/병행 정보 및 기간을 구조화된 **Mock 예시**로 제안하고 상대가 확인해야 진행한다. 원래 서명 조건과 별개인 개발 예시이며 실제 계약 변경이 아니다.
- Mock 기간 1~365일·기록/사유1000자·운송장100자 제한은 개발 입력 보호 범위이며 서비스 계약 상한을 확정하지 않는다.
- D09: 예시 계산만 `모의 시작 시각 + 달력일 수`(시작일 미포함, 동일 한국 시각)로 표시한다. 확정 서비스 규칙이 아니다. 카운트다운/지연은 모의 서버 조회 시각 기준으로 재조회하며 실시간 서버 동기화는 미구현이다.
- 파일 제공은 텍스트 자료명 기록이다. 실제 업로드/저장/검사/다운로드 없음. 운송장은 선택 텍스트이며 주소는 받지 않는다. 배송사 연동 없음.
- 준비 문제·정정은 사유/행위자/시각 이력에 남는다. 시작 후 문제가 생기면 문제 보류를 표시하고 기존 시작/납기는 보존한다. 자동 연장·재시작 없음. 작업 중단의 서비스 정책은 D10 미결정이다.
- WORK-02는 제작 시작 후 같은 계약의 납기 날짜 변경 요청/상대 승인·거절만 시연한다. 원계약/기존 값·이력 보존. 금액/범위/추가금/차감 변경은 D10 조율 전 차단하고 이를 미완료로 기록한다.
- 요청 중복은 ID+내용+행위자를 대조하고 revision으로 충돌을 거부한다. 응답 유실은 조회/동일 명령 재시도로 해결한다. 단일 탭 메모리의 동기 처리이며 실제 DB 트랜잭션/다중 탭/영구 저장/알림은 미검증이다.
- 실패 사례: 미결제·미서명·파일 누락·제품 손상은 시작 불가, 늦은 로그인 응답은 epoch로 차단, 오래된 변경 승인·동일 ID 다른 내용은 거부, 정정/재전송으로 납기 변경 금지. 실제 서버 잠금/서버 시간 검증은 API 협업으로 남긴다.

4-B 납품·검토·수정/최종 수령·정산 및 4단계 전체 통합은 이번 범위 밖이다.
