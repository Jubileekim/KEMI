## 구현 순서

1. **PROJ-01·02** — 공개 맞춤 의뢰 CRUD와 탐색
2. **APPLY-01·02 + STATE-01 + NOTI-01** — 지원, 선정·거절, 자동 마감과 알림
3. **BOOK-01 + REC-01** — 북마크와 목적·스타일 기반 기본 추천
4. **PORT-01 + PACK-01 + ORDER-01~03** — 작품·패키지와 직접 의뢰
5. **FILE-01 + STATUS-01** — 원본 업로드와 거래 현황
6. **AI·합의·계약·서명·테스트 결제·납품·정산·리뷰** — 공통 거래 흐름 완성

페이즈 2 완료 기준은 1~3을 실제 API와 DB로 연결하고, 회원가입부터 프로젝트 지원·선정·알림 수신까지 통합 검증하는 것이다.

## 프로젝트 API 설계 결정

- 프로젝트 소유자는 `users.id`를 직접 참조한다. 프로필 저장은 다른 기능의 선행 조건이 아니기 때문이다.
- 삭제는 행을 지우지 않고 `deleted_at`과 `CLOSED` 상태로 보존한다.
- 공개 목록은 `OPEN`, 미삭제, 모집 마감 전 항목만 노출한다.
- 프로젝트 상태는 모집 중 `OPEN`, 지원자 선정 후 조건 합의 중 `MATCHED`,
  모집 종료 `CLOSED`, 계약 체결 `CONTRACTED`로 구분한다.
- `CLOSED`의 종료 사유는 `MANUAL`, `EXPIRED`, `NO_SELECTION`으로 별도 기록한다.
  `NO_SELECTION`은 상태가 아니라 선정자와 합의 실패 등에 따른 종료 사유다.
- 영상 목적과 영상 스타일은 별도 속성으로 저장한다.
- 금액은 KRW 정수로 저장하고 API에서는 JavaScript 안전 범위 안의 숫자로 반환한다.
- 희망 납품일은 모집 마감일보다 뒤여야 한다.
- 지원·계약 기능이 추가되면 `CONTRACTED` 프로젝트는 수정·삭제할 수 없고, 같은 프로젝트의 나머지 지원을 자동 종료한다.

## 아직 팀 합의가 필요한 값

- 프로젝트 영상 목적·스타일의 최종 화면 표시 이름
- 기존 크리에이터 프로필의 B2B 분야·스타일 값을 B2C 분류로 옮기는 데이터 변환
- MVP 모집 마감은 직접 마감과 요청 시각 검증으로 처리한다. 만료 시점 알림과
  상태 정리를 위한 DB Cron은 후속 작업으로 둔다.
- 공개 프로젝트 수정 가능 시점과 지원자에게 변경을 알릴 범위
- 직접 의뢰 48시간 응답 기한

값이 확정되기 전에도 상태·권한·중복 방지 구조는 먼저 구현하되, 기존 데이터를 파괴하는 마이그레이션은 실행하지 않는다.
