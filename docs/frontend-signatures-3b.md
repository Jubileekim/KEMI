# 3-B 양측 서명·만료·최종 선정

## 근거와 API 대조

- 원본 `케미 기능명세서.xlsx` TERMS-02·CONTRACT-01·TERMS-03, 상태 전이·권한 및 P07/P09/D08을 확인했다. 확인 요청부터48시간, 동일 버전 양측 서명, 두 번째 서명 시 한 후보 선정·모집 종료·타후보 미선정이 확정 기준이다. 변경·만료 시 새 버전으로 재확인하며 이전 서명은 보존하고 재사용하지 않는다. 일반 대화는 만료하지 않는다.
- 수정된 계획 3단계와 `기술 스택.pdf`의 React/Vite·Router·Query·Axios·RHF/Zod·npm Workspaces를 유지한다. 새 의존성·API/shared 변경은 없다. 기존 KEMI 토큰·주요 색 #367345·카드·한국 시간·600/1024px 구간을 사용한다.
- `api문서.txt`와 API/shared에는 조건서·서명·계약 원자 확정 API가 없다. `/api/applications/{applicationId}/accept`는 협의 시작 때 MATCHED/타후보 종료를 수행하므로 P07과 충돌한다. 해당 API를 연결하지 않고 **DEV/MSW `/__mock__/signatures/:requestId`**를 사용한다. 운영은 기존 연결 준비 안내를 유지한다.

## 동작과 실패 경계

1. 최신 저장본의 모든 최종 값을 확인한 뒤 별도 확인창으로 서명 요청한다. 요청 자체는 서명이 아니다. 누락·구버전·revision 충돌·협의 종료를 차단한다. 중복 요청으로 기한을 연장하지 않는다. 저장하지 않은 입력은 서명 대상에 포함하지 않는다고 표시한다.
2. Mock 이름 입력과 명시 동의 후 본인 서명만 추가한다. 한쪽 서명은 계약 미확정이며 후보를 유지한다. 같은 버전의 두 번째 유효 서명만 모의 계약 식별을 만들고 해당 공고의 단일 선정·모집 종료·다른 미처리 후보 미선정을 함께 반영한다. 계약 전후 같은 방·메시지·조건서 사본을 유지하며 미선정 방은 읽기 전용이다. 결제/제작 시작은 발생하지 않는다.
3. 새 작성본 저장 시 이전 요청은 대체됨으로 표시한다. 이전 값/서명/시각을 보존하고 새 버전에는 서명을 복사하지 않는다. 만료 후 같은 버전 재요청은 차단하고 `새 확인 버전 만들기`로 같은 값의 새 작성본을 만든 뒤 다시 요청한다.
4. Bearer·ACTIVE·역할·당사자·방·최신 상태를 검사하고 지연 후 계정 epoch를 다시 검사한다. 클라이언트도 계정/방별 입력·Query를 분리하고 자동 재시도하지 않는다. 응답 유실은 같은 명령/ID 재시도 또는 저장 결과 조회로 확인한다. 알려진400/401/403/404/409는 거절로 처리하고 그 밖의 결과 불명확 상태는 새 ID 실행을 차단한다.

## 미결정과 실제 검증 경계

- **D08 유지:** 이름 최대100자+체크박스, 양 당사자 작성, revision 비교, `현재 시각 >= 만료 시각` 차단은 Mock 검토 후보다. 서명 형식·인증 강도·정확한 경계·서버 시간/시차·동시 편집을 제품 정책으로 확정하지 않는다. 이름 문자열은 법적 서명 검증 증거가 아니다.
- 시간·동기 처리·유일성은 단일 탭 메모리에서만 검증한다. 실제 DB 트랜잭션/잠금 순서·공고당 계약 unique·다중 탭/기기·서버 시간·영구 저장·알림/outbox·전자서명 제공자·실제 API/결제는 미연결/미검증이다. 새로고침하면 초기화된다.
- 공개 제안 협의방에 대한3-B 클라이언트/Mock 범위다. 직접 의뢰 경로 통합·3-C 테스트 결제·3단계 전체 통합은 남아 있다. 실제 운영 보안/계약 완료로 표시하지 않는다.
- 구현 참고: [React Effect 정리](https://react.dev/reference/react/useEffect), [TanStack Query 무효화](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation). 기존 설치 버전/타입과 기존 패턴을 유지한다.
