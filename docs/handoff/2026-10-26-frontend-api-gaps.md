## 2. 선정 모델 충돌 (APPLY-02·CONTRACT-01) — 결정 필요

| 항목        | 지금 백엔드 (#22, `main`)                                                                                                 | 기능명세서·프론트엔드 Mock (#43~#45)                                                         |
| ----------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 의뢰인 행동 | `POST /api/applications/{id}/accept` = **선정**                                                                           | "협의 요청". 여러 후보와 동시에 협의할 수 있다                                               |
| 선정 시점   | accept 즉시. 프로젝트 `MATCHED`, 나머지 대기 지원은 `NOT_SELECTED`(`OTHER_SELECTED`)                                      | **양측이 같은 버전 조건서에 서명하는 순간** (CONTRACT-01 "동시 후보에서 1건만 확정")         |
| 다른 후보   | accept 즉시 자동 거절 + 알림                                                                                              | 서명 전까지 유지. APPLY-02 완료 기준 "협의 시작만으로 선정·자동 거절 안 됨" (P07, 확정 정책) |
| 근거        | 2026-10-23 분담 계획의 "지원자를 선정하면 프로젝트 마감 + 나머지 지원자 자동 거절을 하나의 트랜잭션으로" (결정 기록 12장) | 기능명세서 APPLY-02·CONTRACT-01·CHAT-04·CHAT-05 (P07·P09)                                    |

- 프론트엔드는 이 충돌 때문에 실제 `accept`를 "협의 요청" 버튼에 연결하지 않고, 개발용 Mock(`/__mock__/proposals`)을 쓴다(#43).
- 참고: 결정 기록 2장의 처음 설계와 ERD v0.6 상태 정의는 기능명세서와 같았다.
  - `PENDING`(협의 요청 전) → `DISCUSSING`(협의 중, 조건서·서명 대기 포함) → `CONTRACTED`
  - `NOT_SELECTED` = "다른 후보 계약 또는 무선정 종료"
  - #22에서 분담 계획에 맞춰 "선정 즉시 자동 거절"로 바꿨다.

**선택지**

| 안                        | 내용                                                                                                                                                               | 백엔드 작업                                                                                                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. 기능명세서 기준 (제안) | 협의 요청은 지원을 `DISCUSSING`으로만 바꾼다. 프로젝트·다른 후보는 그대로다. 양측 서명으로 계약이 확정될 때 프로젝트 `CONTRACTED`, 나머지 활성 지원 `NOT_SELECTED` | 협의 요청 API(새로 만들거나 `accept`의 의미 변경), 서명 트랜잭션에서 자동 거절. `MATCHED`의 쓰임 재검토. 테이블·CHECK 값은 이미 있어 **DB 구조 변경은 거의 없다**. #22 테스트·알림 문구 수정 |
| B. 지금 API 유지          | accept = 선정. 협의·조건서는 선정된 한 명하고만 한다                                                                                                               | 백엔드 변경 없음. 대신 기능명세서(APPLY-02·CONTRACT-01·CHAT-05)와 프론트엔드 2-D·3-A·3-B 흐름을 고쳐야 한다                                                                                  |

- A를 택하면 같이 정할 것
  - 동시에 협의할 수 있는 후보 수 상한
  - 협의 중에 모집 마감·무선정 종료(CAMP-06)를 하면 협의를 어떻게 할지 (CAMP-05: "마감이 기존 협의 자동 취소 안 함")
  - 알림: 협의 요청 알림(새 종류)과, 계약 확정 시 미선정 알림의 시점

## 5. 제안하는 백엔드 순서

1. **선정 모델 결정 (2장)** → A안이면 협의 요청 API·철회·무선정 종료(APPLY-02·03, CAMP-06)
2. **조건서·서명·계약** (TERMS-01~03, CONTRACT-01): #44·#45 Mock의 요청·응답 형식을 보고 API 계약을 먼저 맞춘다
3. **테스트 결제** (PAY-01·02): PG Sandbox 선택(#46은 Toss 기준 Mock)
4. **파일 업로드** (FILE-01): 납품·작업물·로고의 선행 조건
5. **제작 준비·납품·수정·수령·정산** (READY·WORK·DEL·REV·SETTLE)
6. 채팅(CHAT-01~05)은 2~5와 병행 가능. Realtime 자체 JWT 검증을 먼저 한다
7. 작은 수정: AUTH-01 비밀번호 규칙, CAMP-01·02 초안·모집 기간, CAMP-05 자동 마감, REC-01 추천 이유

- 기반 작업(`KEMI-dev` DB #24, Render 배포 #27)이 끝나야 실제 API로 E2E(#26)를 할 수 있다.
- API를 추가할 때마다 OpenAPI 문서와 테스트를 함께 고친다(#25, #31).
