# 백엔드 묶음(#51~#64) 배포 전 검증과 운영 반영 절차

작성 2026-10-27. 대상: 쌓인 Draft PR #51 → #53 → #54 → #55 → #56 → #58 → #59 → #60 → #62 → #63 → #64.

## 1. PM 결정

- **선정 모델 A안 확정**(2026-10-27): 협의 요청은 선정이 아니다. 양측이 같은 최종 조건서 버전에 서명할 때 1명을 선정한다.
- **마이그레이션 순서**: 읽기 전용 점검 → 개발 DB 검증 → 기존 데이터 보존·마이그레이션 검토 → 운영 적용.
- 나머지 제안 정책(D11·D12·D13·D14·D16·D18·D21·D22)은 항목별로 확정한다.

`main`은 지금 "수락 즉시 선정"이고 A안은 #54부터 들어 있다. 그래서 **#51~#54는 따로 배포하지 않고 묶음 전체를 이어서 병합한 뒤 한 번에 배포한다**(아래 4장). 중간 상태가 Render에 배포되지 않게 해야 한다.

## 2. 운영 DB 읽기 전용 점검 (2026-10-27)

기존 KEMI Supabase 프로젝트 그대로다. `READ ONLY` 트랜잭션으로만 확인했고, 아무것도 바꾸지 않았다.

- PostgreSQL 17
- 적용된 마이그레이션: `main`의 7개(`20261019051147_auth_tables` ~ `20261023130000_project_discovery`), 모두 완료
- 새 구조 테이블(`users`·`projects`·`work_requests`·`notifications` 등): 0행
- 옛 구조 테이블(대문자 `"Project"`·`"User"`·`"Skill"` 등): `"Skill"` 12행, `"User"` 1행, 나머지 0행. 새 마이그레이션은 이 테이블을 건드리지 않는다.

## 3. 개발 DB 검증 (운영 스키마 복제본)

### 방법

1. 운영 DB에서 **스키마와 `_prisma_migrations` 기록만** `pg_dump`로 읽어 왔다(사용자 데이터는 복사하지 않음).
2. 로컬 PostgreSQL 17에 복원하고, 마이그레이션 전부터 있던 것처럼 합성 데이터를 넣었다.
   - 옛 테이블 행
   - 사용자 3명, 공고 1건
   - 지원 2건(`DISCUSSING`·`PENDING`)
   - 알림 2건(이전 방식의 `APPLICATION_ACCEPTED` 포함)
3. `#64` 브랜치에서 `prisma migrate deploy`를 실행했다.
4. 배포 빌드(`dist/server.js`, `NODE_ENV=production`)를 이 DB에 붙여 실제 HTTP로 전체 흐름을 호출했다.

### 결과

**마이그레이션**

- 19개 모두 적용(기존 7 + 새 12).
- 새 구조 테이블 기준 스키마 차이 0. 남은 차이는 옛 대문자 테이블뿐이며, `migrate deploy`는 이 테이블을 지우지 않는다.

**기존 데이터 보존**

- 마이그레이션 전후 스냅샷의 행 수와 내용이 같다.
- `work_requests`는 새 열(`package_id`, NULL)만 늘었다. 기존 값은 같다.
- `APPLICATION_ACCEPTED` 알림은 바뀌지 않았다(#54 리뷰 반영).

**새 마이그레이션 SQL 점검**

- 기존 데이터를 바꾸는 구문(`UPDATE`·`DELETE`·`DROP TABLE`·`DROP COLUMN`·`RENAME`·`TRUNCATE`)이 없다.

## 4. 운영 반영 절차 (PM 승인 후, 희년님 병합)

1. 위 외부 키 검증을 끝내고 PM이 묶음 병합을 승인한다.
2. Render 자동 배포를 잠시 멈춘다. 중간 상태가 배포되지 않게 하기 위해서다.
3. 운영 DB 백업을 확인한다(Supabase 대시보드 > Database > Backups).
4. 운영 DB에 `prisma migrate deploy`를 실행한다. 새 12개가 적용되는지 `prisma migrate status`로 확인한다.
   - 새 마이그레이션은 테이블·열·제약만 추가한다. 새 열은 NULL 허용이거나, 새 테이블에만 NOT NULL로 붙는다.
   - 따라서 **지금 `main` 코드가 새 스키마에서도 그대로 동작한다.** 마이그레이션을 먼저 적용해도 Render 장애가 나지 않는다.
   - 확인(2026-10-27): `main` 코드에 새 마이그레이션 19개를 얹어 `main`의 DB 테스트를 실행했다.
     - 동작 테스트 196개는 통과했다.
     - 실패 3개는 테이블 목록·CHECK 허용 값을 `main`의 목록과 비교하는 메타 테스트다. 새 테이블·값이 늘었으니 실패가 맞다.
5. PR을 `#51` → … → `#64` 순서로 병합한다. 각 PR의 base가 바로 앞 브랜치라, 앞 PR을 병합한 뒤 다음 PR의 base를 `main`으로 바꾼다.
6. 자동 배포를 다시 켜고, 확인한다.
   - `/health`, `/health/ready`
   - 가입·공고·협의·서명 흐름 1회
7. 시연 데이터는 **운영 DB에 넣지 않는다**(시드가 실제 사용자 있는 DB·허용 목록 밖 DB를 거부한다).
