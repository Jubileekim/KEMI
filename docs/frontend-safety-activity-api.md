# 활동·알림·신고·이용 제한 실제 API 연결

2026-10-27. Claude Code의 로컬 `feat/safety-activity` 커밋과 미커밋 화면을 별도 checkout으로 가져와 이어서 검증했다. #77은 `main`에 병합됐으며 이 작업은 그 후속이다.

## 제공하는 기능

- `GET /api/activity`: 로그인한 당사자의 모집·지원·직접 의뢰·계약 진행 단계와 알림 수를 묶어 조회한다.
- `POST /api/notifications/read`: 선택한 알림 ID만 읽음 처리한다. 다른 사람의 ID가 섞이면 404이며 전체 요청을 반영하지 않는다.
- `POST /api/reports`, `GET /api/reports/me`: 공개 모집 또는 본인이 참여한 의뢰를 신고하고 본인 신고와 경고·제한 안내를 확인한다.
- `POST /api/reports/:id/appeal`: 제한 대상 본인이 이의를 제기한다. 이의 내용은 신고자에게 노출하지 않는다.
- `GET /api/admin/reports`, `POST /api/admin/reports/:id/actions`: 운영자만 근거를 적고 검토·경고·제한·해제한다. 이력은 운영 기록에 남는다.
- `POST /api/analytics/events`, `GET /api/admin/analytics`: 허용한 이벤트 이름·대상 ID·시각을 기록하고 운영자에게 최근 30일 행동 집계를 제공한다. `@kemi.test` 계정은 집계에서 제외한다.

신고 자체는 자동 제재가 아니다. 제한은 새 모집·지원·직접 의뢰에 적용하며 진행 중인 거래 접근은 유지한다. D18·D21·D22 관련 세부 운영 정책은 제안이며 이 구현으로 확정하지 않는다. 행동 기록은 클라이언트가 보낸 탐색 통계이며 결제·계약의 진실 원장이나 정산 근거가 아니다.

## 화면과 기존 PR의 대응

- #73의 내 활동·저장·추천: `/me/activity`, `/bookmarks`, `/recommendations`를 실제 API에 연결했다. 서버가 계산한 단계와 다음 화면을 연결하고, 저장·해제 후 목록을 갱신한다.
- #74의 알림·리뷰: `/notifications`에 선택 읽음·모두 읽음과 상단 알림 수를 연결했다. 리뷰 경로 `/contracts/:id/review`는 기존 실제 정산/리뷰 화면을 사용한다.
- #76의 신고·제한·행동 기록: `/reports/new`, `/ops/reports`를 실제 API에 연결했다. 제한 대상자에게 기존 거래 접근이 유지된다는 안내와 이의 입력을 제공한다.
- `App.tsx`의 각 경로는 하나의 화면만 렌더링한다. 아직 병합하지 않은 #73·#74·#76을 그대로 추가로 병합하면 중복 화면이 생길 수 있으므로 이 대응을 검토한 뒤 원 PR을 정리한다. 이 작업에서 원 PR을 닫거나 Mock 파일을 삭제하지 않았다.
- 개발 Mock에서는 기존 접근 안내와 로그인 흐름을 유지한다. 신규 화면은 실제 API 모드에서 동작한다.

## 이어받으며 수정한 문제

- 비회원의 공개 피드·공개 모집 조회가 토큰 획득에서 실패하지 않도록 공개 요청만 구분했다. 개인 조회·모집 작성 등은 계속 인증을 요구한다.
- 로그아웃/계정 전환 시 전송 대기 중인 행동 기록과 세션 내 중복 집합을 비운다. 실패한 분석 요청은 거래 UI를 막지 않는다.
- 신고자의 조회 및 신고 재전송 응답에서 상대방의 이의 내용을 제거했다. 운영자는 전체 이력을 확인할 수 있다.
- 최근 안내 50건 밖에 제한 기록이 있어도 현재 제한 여부를 정확하게 계산한다.
- 운영 조치·이의 제기의 동일 내용 재시도는 같은 명령 식별자를 사용한다.
