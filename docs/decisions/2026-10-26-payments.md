## 1. 실제 결제 차단 [확정 정책 P10 반영]

- 서버는 Toss **테스트 시크릿 키(`test_sk_`·`test_gsk_`)만** 받는다. `live_` 키를 넣으면 환경 변수 검증에서 서버가 시작하지 않는다(`TOSS_SECRET_KEY`).
- 키가 없으면 주문·승인·조회 경로는 `503 SERVICE_UNAVAILABLE`이고, 다른 기능과 결제 내역 조회는 그대로 동작한다(AI 단가 분석과 같은 방식).
- 테스트 환경의 승인은 가상이라 결제수단에서 금액이 빠지지 않는다(Toss 문서).

## 2. 흐름

1. 의뢰인이 계약 화면에서 "결제"를 누른다. 화면은 UUID를 만들어 `POST /api/contracts/{contractId}/payments { commandId }`.
   - 서버는 계약 금액으로 `READY` 주문을 만든다. **금액은 요청으로 받지 않는다.** `commandId`가 Toss `orderId`가 된다.
2. 화면이 Toss 결제위젯을 연다(`clientKey`는 프론트엔드 환경 변수). 주문의 `orderId`·`amountKrw`·`orderName`을 넘긴다.
3. Toss가 successUrl로 돌려보낸다(`paymentKey`, `orderId`, `amount`). 화면은 그 값을 `POST /api/payments/confirm`으로 보낸다.
   - 서버는 `amount`가 저장한 주문 금액과 같은지 먼저 확인한다. 다르면 Toss를 부르지 않고 `400`이다.
   - 같으면 Toss 승인 API를 부른다. `Idempotency-Key: confirm-{orderId}`로 같은 승인을 여러 번 보내도 한 번만 처리된다.
4. 실패·취소면 Toss가 failUrl로 돌려보낸다. 화면은 `POST /api/payments/{orderId}/fail { code, message }`로 승인 전 주문을 닫는다.
5. 결과를 모르면(`UNKNOWN`) 화면은 `POST /api/payments/{orderId}/sync`로 Toss 조회 결과를 다시 받는다.

## 3. 주문 상태

| 상태        | 언제                                                                      | 다음                                               |
| ----------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
| `READY`     | 주문을 만들었고 승인 전                                                   | 승인 → 아래 셋 중 하나, fail → `FAILED`·`CANCELED` |
| `UNKNOWN`   | 승인을 요청했지만 응답을 받지 못함(시간 초과·네트워크·Toss 5xx·형식 오류) | sync로 `SUCCEEDED`·`FAILED`·`CANCELED`             |
| `SUCCEEDED` | Toss `DONE`이고 주문 번호·금액이 저장한 값과 같음                         | (끝, 환불은 후속)                                  |
| `FAILED`    | Toss가 거절(4xx 코드), `ABORTED`·`EXPIRED`, 결제 기록 없음(조회 404)      | (끝)                                               |
| `CANCELED`  | 사용자 취소(`PAY_PROCESS_CANCELED`), Toss `CANCELED`                      | (끝)                                               |

- 계약당 `READY`·`UNKNOWN`·`SUCCEEDED` 주문은 **하나뿐**이다(부분 UNIQUE `payments_one_active_idx`). 그래서 이중 결제와 결과 불명확 중 새 결제를 막는다.
- `FAILED`·`CANCELED` 주문은 지우지 않고 이력으로 남긴다. 그 뒤에만 새 주문을 만들 수 있다.
- **결과가 불명확하면 실패로 보지 않는다.** Toss 5xx·시간 초과는 실제로 승인됐을 수 있어서 `UNKNOWN`으로 두고 조회로 맞춘다.
- Toss가 `DONE`을 돌려줘도 주문 번호·금액이 다르면 `SUCCEEDED`로 인정하지 않고 `UNKNOWN`으로 둔다(로그를 남긴다).
- Toss 키 문제(`UNAUTHORIZED_KEY`·`INVALID_API_KEY`·`INCORRECT_BASIC_AUTH_FORMAT`)는 서버 설정 오류라 주문 상태를 바꾸지 않고 `503`이다.
- `ALREADY_PROCESSED_PAYMENT`(이미 처리됨)면 Toss 조회로 저장된 결과를 받아 반영한다.

## 4. 동시성과 멱등

- 주문 생성·승인·조회·실패 처리는 모두 **계약 행을 `FOR UPDATE`로 잠근** 트랜잭션에서 한다. 같은 주문에 승인이 두 번 들어와도 뒤의 것은 앞의 결과를 보고 처리된다.
- 승인 API 호출(최대 10초) 동안 잠금을 쥐고 있다. 트랜잭션 제한은 30초다. 한 계약의 결제만 기다리게 하므로 MVP 규모에서는 문제가 없다고 본다.
- 재전송
  - 같은 `commandId`의 주문 생성 → 기존 주문(`200`)
  - 같은 `paymentKey`로 이미 `SUCCEEDED`인 주문의 승인 → 기존 결과(`200`)
  - Toss에도 같은 `Idempotency-Key`를 보내므로, 우리 서버가 응답을 잃고 다시 보내도 Toss가 중복 승인하지 않는다.

## 5. 권한

- 주문 생성·승인·실패 기록: 계약의 **의뢰인**만(크리에이터는 `403`)
- 내역 조회·결과 다시 확인(sync): 계약 **당사자** 모두
- 당사자가 아니면 `404`(존재를 드러내지 않음)
