### 헬스 체크 경로 [확정 · PR #1 구현]

- `GET /health`(생존 확인), `GET /health/ready`(DB 연결 확인). 서비스 API는 `/api/*`에 둔다.
- 처음 논의한 `/api/health`와 다른 이유는 두 가지다.
  - Render 헬스 체크는 Vercel rewrite를 거치지 않고 Render 주소로 직접 호출된다.
  - `/api/*`에 붙일 인증·요청 제한 미들웨어와 분리하기 위해서다.
- 프론트엔드의 배포 연결 확인(Plan1 1주차)은 Render 주소의 `/health`를 직접 호출한다.
- Render Health Check Path는 `/health`로 설정한다.

### DB 연결

- [확정] 실제 배포 환경과 Supabase 공식 문서에 맞춰 주소를 고른다. "실행용 6543, 마이그레이션용 직접 연결"을 전제하지 않는다.
- [제안] Render(상시 실행 서버)는 Session pooler 하나로 실행과 마이그레이션을 함께 한다. 마이그레이션 주소를 따로 둬야 하면 `MIGRATION_DATABASE_URL`을 쓴다.
- [검증 필요] Render에서 Session pooler 연결, Direct connection(IPv6) 사용 가능 여부
- [확정] 개발 DB와 테스트 DB를 분리하고, 테스트가 팀 공용 DB를 초기화하지 않게 한다. 테스트 DB 종류(로컬 Docker / 테스트 전용 Supabase)는 결정이 필요하다.

### 채팅 Realtime

- [확정] 메시지 저장·조회는 Express API가 참여자 권한을 확인하며 처리한다. Supabase Realtime은 "새 메시지" 신호에만 쓴다.
- [확정] 신호만 보내더라도 비공개 채널 구독 권한을 검사한다.
- [확정] Realtime 연결이 끊겨도, 마지막으로 받은 메시지 이후를 API로 다시 조회해 누락을 복구할 수 있어야 한다.
- [검증 필요] KEMI는 Supabase Auth가 아닌 자체 JWT를 쓴다. Realtime 비공개 채널 인증에 자체 토큰을 연결하는 방법을 작은 검증으로 먼저 확인한다.
- [제안] 검증 전에는 일정 주기로 조회하는 방식으로 동작하게 하고, Realtime은 검증 후에 붙인다.

### 기한 처리

- [확정] 마감 시각은 DB에 저장하고, `서버 현재 시각 ≥ DB 마감 시각`으로 판정한다. cron 실행 여부와 관계없이 조회·처리 API가 만료된 요청을 직접 차단한다.
- [확정] cron(node-cron)은 상태 정리·알림 생성의 보조 수단이다.
- [확정] 서버를 재시작하면 놓친 정리 작업을 한 번 실행한다. Render 무료 플랜은 잠들 수 있기 때문이다.
- [확정] 정리 작업은 조건부 UPDATE로 작성해, 여러 번 실행돼도 결과가 같게 한다.

## 1. 이메일과 소셜 계정 [확정]

- `users.email`은 이메일 로그인용 주소다. 소셜 전용 가입자는 `NULL`을 허용한다.
  - [제안] 정규화 기준: 앞뒤 공백 제거 + 전체 소문자. 정규화한 값에 UNIQUE를 건다. PostgreSQL UNIQUE는 `NULL`을 서로 다른 값으로 보므로, 소셜 전용 회원이 여러 명이어도 충돌하지 않는다.
- 소셜 제공 이메일은 `auth_identities.provider_email`(선택)에 따로 저장한다.
- 소셜 계정 식별 기준은 `(provider, provider_user_id)` UNIQUE다.
  - ERD v0.6의 `provider_subject` 컬럼은 `provider_user_id`로 이름을 바꾼다.
- 같은 이메일이라는 이유로 자동 병합하지 않는다.
- 소셜 전용 계정(`password_hash`가 `NULL`)은 이메일·비밀번호 로그인을 할 수 없다.
- 계정 연결 기능은 MVP 범위에서 제외한다.

## 2. 공고당 계약 최대 한 개

**정책 [확정]**

- 공개 모집에서는 공고당 최종 체결 계약이 최대 한 개다.
- 같은 조건서 버전에 양측이 서명해야 계약이 체결된다.
- MVP에서는 계약 취소 후 같은 공고를 다시 열거나 다른 후보와 재계약하지 않는다. 재모집은 새 공고로 한다.
- 직접 의뢰는 `project_id = NULL`이므로 공고 제약과 별개의 거래다.
- 계약 취소와 결제 환불 완료는 별도 상태로 관리한다.

**제약 설계 [제안]**

계약 초안과 무효 조건서가 어디에 저장되는지 먼저 확인한 뒤 제약을 정했다.

- ERD v0.6에서 계약 전 초안·수정·무효 처리는 모두 `terms_versions`에서 이뤄진다. 상태는 `DRAFT / SIGNING / SIGNED / SUPERSEDED / EXPIRED / VOID`이고, 무효 조건서도 삭제하지 않고 보존한다.
- `contracts` 행은 같은 버전의 두 번째 유효 서명 시점에 처음 생성된다. 초안 단계의 계약 행은 없다.
- 따라서 `contracts.project_id`의 제약은 초안이나 무효 조건서와 부딪히지 않는다.
- 취소된 계약을 제외하는 부분 인덱스(`WHERE status <> 'CANCELLED'`)를 쓰면 취소 후 재계약이 허용된다. 이는 위 정책과 맞지 않는다.
- 결론: 검토 결과 `contracts.project_id` UNIQUE(NULL 제외)가 정책과 정확히 맞는다. 취소된 계약 행도 남아 있어서 같은 공고의 두 번째 계약을 계속 막는다.
- `contracts.work_request_id`, `contracts.terms_version_id`도 UNIQUE를 유지한다.
- `terms_versions`
  - `(work_request_id, version_no)` UNIQUE
  - 요청당 `SIGNING` 버전은 최대 1개: `(work_request_id) WHERE status = 'SIGNING'` 부분 UNIQUE
- `signatures (terms_version_id, user_id)` UNIQUE

**두 번째 서명 트랜잭션 [제안]**

다음을 하나의 트랜잭션으로 처리한다.

1. 공고 행을 `SELECT … FOR UPDATE`로 잠근다 (공개 모집일 때).
2. 서명 대상 버전이 `SIGNING`이고 만료 전이며 해시가 일치하는지 확인한다.
3. 서명을 INSERT하고, 버전을 `SIGNED`로 바꾼다.
4. `contracts`를 INSERT한다. UNIQUE 위반이면 롤백하고 `409 CONFLICT`("이미 다른 후보와 계약이 확정됨")로 응답한다.
5. 요청을 `CONTRACTED`로, 공고를 `CONTRACTED`로 바꾼다(모집 마감).
6. 같은 공고의 다른 활성 요청은 `NOT_SELECTED`로, 그 요청들의 미확정 조건서는 `VOID`로 바꾼다.
7. 관련 알림(`notifications`)을 INSERT한다. `(recipient_user_id, event_key)` UNIQUE로 중복 생성을 막는다.

공고 행 잠금이 1차 방어이고, UNIQUE는 마지막 방어선이다.

**취소와 환불 [확정]**

- 계약 취소: `contracts.status = CANCELLED`
- 환불 완료: `refunds.status = SUCCEEDED`
- 계약 취소만으로 환불 완료로 표시하지 않는다.

## 3. 공개 모집 지원 중복

**정책 [확정]**

- 같은 크리에이터는 같은 공고에 중복 지원할 수 없다.
- MVP에서는 철회한 뒤에도 같은 공고에 재지원할 수 없다.
- 직접 의뢰의 반복 거래는 이 제약으로 막지 않는다.
- 네트워크 재시도로 같은 요청이 중복 생성되는 것은 별도로 막는다.
- 지원 가능 여부는 권한·모집 상태·마감 시각까지 서버에서 확인한다.

**상태 정의 대조** (`work_requests.status`, ERD v0.6)

| 상태           | 의미                                 | 활성 여부   |
| -------------- | ------------------------------------ | ----------- |
| `PENDING`      | 제출됨, 의뢰인의 협의 요청 전        | 활성        |
| `DISCUSSING`   | 협의 중 (조건서 작성·서명 대기 포함) | 활성        |
| `CONTRACTED`   | 계약 확정                            | 종료 (성공) |
| `DECLINED`     | 거절됨                               | 종료        |
| `WITHDRAWN`    | 크리에이터가 철회                    | 종료        |
| `EXPIRED`      | 응답 기한 만료 (주로 직접 의뢰)      | 종료        |
| `NOT_SELECTED` | 다른 후보 계약 또는 무선정 종료      | 종료        |

- [제안] 활성 상태는 `PENDING`, `DISCUSSING` 두 가지다. 화면 표시와 "진행 중 지원" 집계에 쓴다.
- 재지원을 금지하므로, 중복 제약은 활성 상태만이 아니라 **모든 상태**에 걸어야 한다. 활성 상태에만 부분 UNIQUE를 걸면 철회 후 재지원이 허용돼 정책과 어긋난다.

**제약 [제안]**

- `work_requests (project_id, creator_id)` UNIQUE.
  - 공개 지원은 `project_id`가 있으므로 공고당 크리에이터 1건만 존재할 수 있다.
  - 직접 의뢰는 `project_id = NULL`이라 이 제약을 받지 않는다.
- CHECK: `request_type = 'PROJECT_APPLICATION'`이면 `project_id IS NOT NULL`, `DIRECT_REQUEST`이면 `project_id IS NULL`.

**API 검사** (DB 제약만으로 부족한 부분)

- 공고가 `OPEN`이고, 서버 현재 시각이 `recruitment_end_at` 이전인지
- 지원자 역할이 `CREATOR`이고, 공고 작성자 본인이 아닌지
- 첨부한 패키지·포트폴리오가 지원자 소유인지
- UNIQUE 위반은 `409 CONFLICT`("이미 지원한 공고")로 응답

**직접 의뢰 중복 생성 방지 [제안]**

- `work_requests.client_request_key` 컬럼을 추가하고 `(client_id, client_request_key)` UNIQUE를 건다. ERD v0.6에 없는 컬럼이다.
- 클라이언트는 의뢰 작성 화면을 열 때 UUID를 만들고, 재시도할 때 같은 값을 보낸다.
- 서버는 같은 키가 이미 있으면 새로 만들지 않고 기존 요청을 반환한다.

## 4. 파일 업로드

**한도와 형식 [확정]** (무료 MVP 기준)

| 종류   | 파일당 한도 | 허용 형식           |
| ------ | ----------- | ------------------- |
| 영상   | 50MB        | MP4, MOV            |
| 이미지 | 10MB        | JPG·JPEG, PNG, WebP |
| ZIP    | 50MB        | ZIP                 |

- Supabase 무료 플랜의 파일당 업로드 한도(50MB)에 맞췄다. 유료로 전환할 때 다시 정한다.

**흐름 [확정]**

1. Express가 권한을 확인하고 업로드 권한(서명 URL)을 발급한다.
2. 브라우저가 Supabase Storage로 직접 업로드한다.
3. 업로드가 끝나면 서버가 실제 파일의 소유권·크기·형식을 확인한 뒤 업무 데이터에 연결한다.

- 계약 자료와 납품물은 비공개 버킷에 둔다. 다운로드·미리보기 URL을 발급할 때도 참여자 권한을 확인한다.

**검사 방식 [제안]**

- 발급할 때: 선언한 크기·MIME 형식·업로드 목적, 대상 리소스의 소유권과 거래 당사자 여부
- 완료를 확인할 때:
  - Storage 객체의 실제 크기를 확인한다.
  - 확장자를 믿지 않고 파일 앞부분(매직 바이트)을 읽어 실제 형식을 판정한다. MP4·MOV는 `ftyp`, PNG·JPEG·WebP·ZIP은 각자의 시그니처로 판정한다.
  - 업로더와 `files.owner_id`가 같은지 확인한다.
  - 하나라도 실패하면 `files.status = REJECTED`로 표시한다.
- 추가 방어: Supabase 버킷 설정에도 같은 크기·MIME 제한을 건다.
- [검증 필요] 영상은 끊겨도 이어서 올릴 수 있는 업로드(Supabase의 TUS 재개 가능 업로드)를 검토한다. Supabase는 6MB가 넘는 파일에 이 방식을 권장한다. 서명 URL 방식과 함께 쓸 수 있는지, 권한 발급과 어떻게 연결할지 먼저 확인한다.

**기존 300MB 표기 수정 대상**

| 문서       | 위치                                               | 수정 내용                                               |
| ---------- | -------------------------------------------------- | ------------------------------------------------------- |
| PRD        | 15.6 파일과 편집 원본 ("300MB는 파일당 한도 후보") | 위 표로 변경. 300MB는 유료 전환 시 재검토               |
| PRD        | 24장 기능명세 확정 항목 "파일" 행                  | 300MB 적용 단위 → 위 표로 확정                          |
| 기능명세서 | FILE-01 (파일 업로드)                              | 한도·형식·검사 단계 반영                                |
| ERD v0.6   | `files` 업무 규칙 ("300MB 적용 단위는 D17 미결정") | 위 표로 교체                                            |
| ERD v0.6   | 미결정 D17                                         | 크기·형식 확정. ZIP 내부 검사와 보관 기간만 미결로 남김 |

## 5. 인증 토큰

**확정 사항 [확정]**

- Access/Refresh 토큰을 쓴다.
- 수명
  - Access 토큰: 15분
  - 로그인 세션(Refresh 토큰 계열): 로그인 시점부터 최대 7일. 회전해도 이 기한은 늘어나지 않는다.
- Refresh 토큰은 해시로만 저장하고, 회전 이력을 보존한다.
- 기존 토큰을 사용 처리하는 일과 새 토큰을 발급하는 일은 한 트랜잭션에서 처리한다.
- 두 종류의 폐기를 구분한다.
  - 회전으로 "사용 처리된" 개별 토큰
  - 로그아웃·탈취 감지로 "폐기된" 로그인 세션 전체
- Access 토큰에 담긴 세션 ID는 회전 때문에 무효화되지 않는다.
- 동시 갱신 유예는 초기값 10초다. 유예 시간은 이미 사용한 토큰으로 새 토큰을 다시 발급해 주는 시간이 **아니다**.
- 프론트엔드는 갱신 요청을 하나로 모은다. 서버는 정상적인 동시 요청과 재사용(탈취 의심)을 구분한다.

**식별자 [확정]**

- PK·FK는 ERD v0.6대로 `bigint`다.
- API 응답과 JWT의 `sub`(사용자 ID)·`sid`(세션 ID)는 문자열로 보낸다(예: `"42"`).
- `JSON.stringify`는 `BigInt`를 직렬화하지 못한다. 그래서 응답을 만들 때 서버가 `bigint`를 문자열로 바꾸고, 요청으로 받은 ID는 숫자 형식인지 검증한 뒤 `BigInt`로 바꾼다.

**테이블 구조 [확정]**

ERD v0.6의 `auth_sessions` 한 테이블을 둘로 나눈다. ERD 변경 명세는 [docs/erd/erd-v0.6-changes.md](../erd/erd-v0.6-changes.md)에 있다. 개별 토큰의 "사용됨"과 세션 전체의 "폐기됨"이 서로 다른 행에 기록되므로, 위의 두 가지 폐기가 자연스럽게 구분된다.

`auth_sessions` — 로그인 세션 1건 = 토큰 계열 1개

| 컬럼                          | 설명                                                              |
| ----------------------------- | ----------------------------------------------------------------- |
| `id` bigint PK                | Access 토큰의 `sid`. 회전해도 바뀌지 않는다                       |
| `user_id`                     | 회원                                                              |
| `expires_at`                  | 로그인 시각 + 7일. 회전해도 바꾸지 않는다                         |
| `revoked_at`, `revoke_reason` | 세션 전체 폐기 시각과 사유(`LOGOUT` / `REUSE_DETECTED` / `ADMIN`) |
| `last_used_at`                | 마지막 갱신 시각                                                  |
| `created_at`                  | 로그인 시각                                                       |

`auth_refresh_tokens` — 개별 Refresh 토큰

| 컬럼                    | 설명                                     |
| ----------------------- | ---------------------------------------- |
| `id` bigint PK          |                                          |
| `session_id` FK         | 소속 세션 (앞서 말한 `family_id`의 역할) |
| `token_hash` UNIQUE     | 토큰 원문의 SHA-256 해시                 |
| `used_at`               | 회전에 사용된 시각. NULL이면 아직 유효   |
| `replaced_by_id` UNIQUE | 이 토큰 대신 발급된 다음 토큰            |
| `created_at`            | 발급 시각                                |

- 앞서 합의한 `family_id`·`replaced_by_id`·`last_used_at`의 역할은 모두 유지된다. 다만 `family_id`는 `session_id` FK가 된다.
- Refresh 쿠키의 `Max-Age`는 세션 `expires_at`까지 남은 시간으로 정한다.

**회전 절차 [확정 · 구현]** (`apps/api/src/auth/auth.service.ts`)

`POST /api/auth/refresh` 하나를 처리하는 순서:

1. 쿠키의 토큰을 해시해서 `auth_refresh_tokens` 행과 소속 세션·회원을 읽는다.
2. 토큰이 없거나, 세션이 폐기됐거나, 세션이 만료(`expires_at ≤ now`)됐으면 `401 SESSION_REVOKED`로 응답하고 쿠키를 삭제한다. 회원이 이용 불가 상태면 `403`이다.
3. `used_at`이 NULL이면 한 트랜잭션에서 회전한다.
   - 세션을 조건부 UPDATE(`revoked_at IS NULL AND expires_at > now`)로 `last_used_at`을 갱신한다. 이때 세션 행이 잠기고, 0건이면 그사이 폐기된 것이라 `401`이다.
   - 새 토큰 행을 INSERT한다.
   - 이전 토큰을 조건부 UPDATE(`id = 이전 토큰 AND used_at IS NULL`)로 `used_at`과 `replaced_by_id`를 기록한다. 0건이면 다른 요청이 먼저 회전한 것이라 트랜잭션을 되돌리고 4번 판정으로 넘어간다.
   - 커밋한 뒤 `200`과 새 Access 토큰, 새 쿠키를 응답한다.
4. `used_at`이 이미 있으면:
   - `now − used_at ≤ 10초`: 정상적인 동시 요청으로 본다. **새 토큰을 발급하지 않고**, 세션도 폐기하지 않는다. `409 REFRESH_RACE`(`details.retryAfterMs: 500`)로 응답하고 쿠키는 건드리지 않는다.
   - 10초 초과: 재사용(탈취 의심)으로 본다. 세션에 `revoked_at = now`, `revoke_reason = REUSE_DETECTED`를 기록하고, `401 SESSION_REVOKED`로 응답하며 쿠키를 삭제한다.

- 처음 설계는 `SELECT … FOR UPDATE`였지만, 같은 효과를 내는 조건부 UPDATE로 구현했다. PostgreSQL은 같은 행을 UPDATE하려는 두 번째 트랜잭션을 첫 번째가 끝날 때까지 기다리게 하고, 끝난 뒤 조건(`used_at IS NULL`)을 다시 확인한다. 그래서 같은 토큰으로 온 두 요청이 모두 새 토큰을 받는 일은 없다. Prisma 기본 API로 작성할 수 있어 raw SQL과 결과 타입 단언이 필요 없다.

**갱신 실패와 재시도 정책 [제안]**

`409 REFRESH_RACE` 뒤에 한 번 재시도한다고 반드시 성공한다고 가정하지 않는다. 브라우저에 새 쿠키가 아직 저장되지 않았거나, 첫 응답이 아예 도착하지 않았을 수 있기 때문이다.

클라이언트가 지킬 규칙 (프론트엔드 구현 기준)

1. **한 탭 안:** 갱신 요청은 하나의 Promise로 모은다(single-flight). `401 TOKEN_EXPIRED`를 받은 요청들은 이 갱신 결과를 함께 기다린 뒤, 원래 요청을 한 번만 다시 보낸다.
2. **여러 탭:** 같은 출처(origin)의 탭끼리 Web Locks API(`navigator.locks.request('kemi-auth-refresh', …)`)로 갱신을 한 번에 하나만 실행한다.
   - 잠금을 기다리던 탭은 잠금을 얻은 시점에 이미 새 쿠키를 갖고 있으므로, 대부분 바로 성공한다.
   - Web Locks를 지원하지 않는 환경에서는 3번의 409 처리만으로 동작한다.
3. **`409 REFRESH_RACE`를 받으면:** 같은 갱신 시도 안에서 최대 2번만 다시 시도한다.
   - 간격은 500ms, 그다음 1,000ms다. 응답의 `details.retryAfterMs`가 있으면 그 값을 따른다.
   - 첫 요청부터 마지막 재시도까지 3초를 넘기지 않는다. 서버의 유예 시간(10초) 안에서 끝내서, 오래된 토큰을 유예 시간 뒤에 다시 보내 재사용 감지를 일으키지 않기 위해서다.
4. **복구할 수 없을 때:** 메모리의 Access 토큰을 지우고 "다시 로그인해주세요" 안내와 함께 로그인 화면으로 보낸다. 무한 재시도는 금지한다. 해당하는 경우는 다음과 같다.
   - 재시도 횟수를 다 썼는데 여전히 `409`
   - `401 SESSION_REVOKED`
   - 네트워크 오류가 2번 연속

상황별 동작

| 상황                                                            | 일어나는 일                                                                                                                            | 결과                                                                                                   |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 새 쿠키가 저장되기 전에 재시도                                  | 재시도가 아직 이전 토큰을 보낸다. 10초 안이라 다시 `409`를 받고, 새 토큰은 발급되지 않는다                                             | 다음 간격 뒤 재시도. 그사이 새 쿠키가 저장되면 성공, 끝까지 아니면 재로그인                            |
| 여러 탭이 동시에 갱신                                           | Web Locks가 있으면 순서대로 실행돼 첫 탭만 회전하고 나머지는 새 쿠키로 성공. 없으면 서버 잠금으로 하나만 200, 나머지는 `409` 후 재시도 | 정상이면 모든 탭 복구, 실패한 탭만 재로그인                                                            |
| 첫 응답 유실 (서버는 회전했는데 응답이 도착하지 않음)           | 브라우저에는 이전 토큰만 남는다. 재시도는 10초 안에서 계속 `409`다. 서버는 이미 사용한 토큰에 새 토큰을 다시 주지 않는다               | 재시도를 다 쓰면 재로그인. 이 세션은 클라이언트가 더 쓸 수 없고, 7일 만료나 다음 재사용 감지 때 끝난다 |
| 응답 유실 뒤 10초가 지나 이전 토큰이 다시 들어옴 (예: 새로고침) | 서버는 재사용으로 판단하고 세션 전체를 폐기한다 (`REUSE_DETECTED`)                                                                     | 재로그인. 탈취가 아닌데도 폐기되는 경우지만, 영향은 그 세션 하나에 그친다                              |

- 서버는 토큰 원문을 저장하지 않는다. 그래서 응답이 유실됐을 때 같은 새 토큰을 다시 보내 줄 방법이 없다. 이 경우의 복구 수단은 재로그인으로 정한다.
- `409 REFRESH_RACE` 응답 예: `{ "error": { "code": "REFRESH_RACE", "message": "다른 요청이 먼저 갱신했습니다. 잠시 후 다시 시도해주세요.", "details": { "retryAfterMs": 500 } } }`

**10초 유예와 재사용 감지의 한계 [확정 · 현재 정책 유지]**

이 정책은 **이미 사용된 토큰이 다시 쓰이는 것을 탐지**하는 장치다. 탈취 자체를 막지는 못하고, 정상적인 사용 중에도 다시 로그인해야 하는 경우가 생길 수 있다.

- **응답 유실:** 서버는 회전했는데 응답(새 쿠키)이 브라우저에 도착하지 못하는 경우다. 네트워크 끊김, 탭 종료, 모바일 백그라운드 전환 등에서 생긴다.
  - 브라우저에는 이미 사용된 이전 토큰만 남는다.
  - 10초 안의 재시도는 `409`만 받고, 서버는 같은 새 토큰을 다시 줄 수 없다(원문을 저장하지 않기 때문).
  - 결과적으로 사용자는 다시 로그인해야 한다.
- **10초가 지난 뒤 이전 토큰이 다시 오는 경우:** 예를 들어 응답 유실 뒤 새로고침하면, 탈취가 아니어도 재사용으로 판단해 그 로그인 세션을 폐기한다(`REUSE_DETECTED`). 다른 기기·브라우저의 세션은 영향을 받지 않는다.
- **아직 사용되지 않은 토큰을 공격자가 먼저 갱신하는 경우 (막지 못한다):**
  - 공격자는 `200`과 새 토큰을 받는다. 서버는 공격자와 정상 사용자를 구분할 수 없다.
  - 정상 사용자의 브라우저에는 이제 "사용된" 토큰이 남는다. 사용자가 10초 안에 갱신하면 `409`만 받고, 10초가 지난 뒤 갱신하면 재사용으로 감지돼 그 세션 전체가 폐기된다. 이때 공격자가 받은 토큰과 Access 토큰도 함께 막힌다.
  - 즉 공격자는 정상 사용자가 다음에 갱신을 시도할 때까지 세션을 계속 쓸 수 있다. 사용자가 다시 접속하지 않으면 탐지되지 않고, 세션 최대 수명(로그인 후 7일)까지 이어질 수 있다.
- **이미 사용된 토큰을 공격자가 쓰는 경우:** 10초 안이면 `409`로 끝나 새 토큰은 받지 못하지만, 재사용으로 탐지되지도 않는다. 10초가 지나면 탐지돼 세션이 폐기된다.
- **Access 토큰을 직접 탈취한 경우:** 회전과 관계없이 만료(15분) 전까지, 또는 로그아웃·재사용 감지로 세션이 폐기되기 전까지 쓸 수 있다.
- 1차 방어는 토큰이 새지 않게 하는 것이다(Refresh 토큰은 `HttpOnly` 쿠키라 스크립트가 읽을 수 없고, Access 토큰은 메모리에만 둔다). 재사용 감지는 새어 나간 뒤의 피해를 줄이는 보조 수단이다.
- **여러 탭:** 프론트엔드가 Web Locks로 갱신을 하나로 모으지 않으면 409가 자주 생기고, 재시도 한도를 넘긴 탭은 재로그인 화면으로 간다.
- 이 한계는 현재 정책으로 감수한다. 재로그인 빈도가 문제가 되면 유예 시간이나 정책을 다시 검토한다.

**로그아웃 [제안]**

- 세션에 `revoked_at`, `revoke_reason = LOGOUT`을 기록하고 쿠키를 삭제한다.
- 이후 Refresh 요청은 `401`이다. 아직 만료되지 않은 Access 토큰도 다음 요청부터 `401`이다(8장 Access 토큰 검증).

**비밀번호 해시 [확정]**

- `bcrypt`, cost 12를 쓴다.
- 확인 결과 (2026-10-19, 이 PC의 Windows · Node 24.18, 저장소 밖 임시 폴더)
  - `bcrypt@6.0.0`의 설치, 해시, 비교가 성공했다. 맞는 비밀번호는 `true`, 틀린 비밀번호는 `false`로 나왔다.
  - cost 12 해시 1회는 약 200ms 걸렸다.
  - 패키지에 미리 빌드된 바이너리(`win32-x64`, `linux-x64` 등)가 들어 있어 네이티브 빌드 없이 로드됐다.
  - npm 11은 설치 스크립트(`node-gyp-build`)를 실행하지 않았다는 경고를 낸다. 미리 빌드된 바이너리로 정상 동작했다.
- [검증 필요] Render와 GitHub Actions(Linux x64)에서의 설치·실행은 인증 PR의 CI·배포에서 확인한다.
- bcrypt는 72바이트 이후를 무시하므로, 입력 검증에서 비밀번호 길이를 72바이트 이하로 제한한다.

**오류 응답 [확정]**

- 형식: `{ error: { code, message, details? } }`
- `details`에는 공개해도 되는 정보만 넣는다. 예: 검증 실패 필드의 경로와 메시지.
- 스택, SQL, 토큰, 해시, 내부 ID 같은 정보는 넣지 않는다.
- [제안] 인증 오류 코드

| 코드                   | 상태 | 언제                                                                         |
| ---------------------- | ---- | ---------------------------------------------------------------------------- |
| `VALIDATION_FAILED`    | 400  | 입력 검증 실패 (`ADMIN` 가입 요청 포함)                                      |
| `EMAIL_ALREADY_EXISTS` | 409  | 이미 가입된 이메일                                                           |
| `INVALID_CREDENTIALS`  | 401  | 이메일이 없거나, 비밀번호가 틀리거나, 소셜 전용 계정일 때 (모두 같은 메시지) |
| `TOKEN_EXPIRED`        | 401  | Access 토큰 만료 (프론트엔드는 갱신 시도)                                    |
| `UNAUTHENTICATED`      | 401  | Access 토큰이 없거나 잘못됨                                                  |
| `SESSION_REVOKED`      | 401  | 세션 폐기·만료, 재사용 감지                                                  |
| `REFRESH_RACE`         | 409  | 유예 안의 동시 갱신. `details.retryAfterMs` 포함 (위 재시도 정책)            |
| `FORBIDDEN`            | 403  | 회원 상태가 이용 불가(제한·탈퇴)                                             |

**저장·쿠키·CSRF·OAuth [제안]**

- Vercel rewrite로 `/api/*`를 Render로 전달해, 브라우저 입장에서 프론트엔드와 API가 같은 도메인이 되게 한다.
- Refresh 토큰: `HttpOnly; Secure; SameSite=Lax; Path=/api/auth` 쿠키
- Access 토큰: 응답 본문으로 받아 메모리에만 보관한다. localStorage에 저장하지 않는다.
- CSRF: 쿠키가 실리는 엔드포인트(refresh·logout)는 `SameSite=Lax`, `Origin` 헤더 검사, `Content-Type: application/json` 요구로 막는다.
- OAuth: 콜백 주소를 Vercel 도메인의 `/api/auth/{provider}/callback`으로 통일하고, `state` 값을 검증한다.
- [검증 필요] rewrite를 거친 쿠키 설정·OAuth 콜백 동작을 실제 Vercel·Render 배포에서 확인한다.

**Access 토큰 검증 [확정]**

- 서명과 만료만 보지 않는다. 요청마다 DB에서 다음을 확인한다.
  1. 토큰의 `sid`에 해당하는 `auth_sessions` 행이 폐기되지 않았는지(`revoked_at IS NULL`)
  2. 그 세션의 `expires_at`이 지나지 않았는지
  3. 회원 상태가 `ACTIVE`인지
- 회전은 `auth_refresh_tokens`에만 기록되고 세션 행은 그대로이므로, 회전한 뒤에도 기존 Access 토큰은 만료 전까지 계속 유효하다.
- 로그아웃이나 재사용 감지로 세션이 폐기되면, 만료되지 않은 Access 토큰도 바로 막힌다.
- [제안] 실패 응답: 세션 폐기·만료는 `401 SESSION_REVOKED`, 회원 제한·탈퇴는 `403 FORBIDDEN`
- [제안] 비용: 요청마다 조회가 1회(세션과 회원을 함께 조회) 늘어난다. MVP 규모에서는 감수한다.

**실제 DB로 검증할 테스트 [확정]**

| 시나리오          | 기대 결과                                                                                                                                                                                                            |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 회원가입          | 201, 비밀번호는 bcrypt 해시로만 저장, 응답에 해시·토큰 해시 없음                                                                                                                                                     |
| 이메일 중복 가입  | 대소문자·공백만 다른 이메일도 `409 EMAIL_ALREADY_EXISTS`                                                                                                                                                             |

**동시 갱신 테스트 방법 [확정]**

- 테스트 파일을 순서대로 실행하는 것(파일 사이의 격리)과, 테스트 안에서 동시 요청을 검증하는 것은 별개다. 동시 갱신은 테스트 안에서 실제로 동시에 보낸다.
- 같은 Refresh 쿠키를 붙인 요청 두 개를 `Promise.all`로 동시에 보낸다. supertest가 요청마다 실제 포트로 서버를 띄우므로, 두 요청은 서로 다른 DB 연결에서 동시에 처리된다.
- 두 요청이 실제로 겹쳤는지 확인한다. 인증 서비스에는 테스트에서만 넣는 지점(`beforeRotationCommit`)이 있다. 첫 요청이 토큰 행을 잠근 직후 이 지점에서, 다른 요청이 DB에서 잠금을 기다리는 중인지(`pg_stat_activity`의 `wait_event_type = 'Lock'`) 별도 연결로 확인하고 결과를 기록한다. 결과가 `[true]`(회전은 한 번, 그동안 다른 요청은 대기)여야 통과한다.
  - 나중에 보낸 요청도 409를 받으므로, 이 확인 없이는 동시성을 검증했다고 할 수 없다.
  - 이 지점은 운영 코드에서는 넘기지 않아 아무 일도 하지 않는다.
  - 검증: 회전 코드에서 `used_at IS NULL` 조건을 일부러 빼면 두 요청이 모두 회전해 이 테스트가 실패하는 것을 확인했다.
- 테스트용 Prisma 연결 수(`DATABASE_POOL_MAX`)는 2 이상으로 둔다. 연결이 하나면 두 트랜잭션이 동시에 열리지 못해 동시성을 검증할 수 없다.
- 어느 요청이 이길지는 고정하지 않는다. "200 하나 + 409 하나"라는 결과만 확인한다.
- 같은 테스트를 여러 번(예: 5회) 반복해서, 우연히 통과하는 경우를 줄인다.
- DB 테스트 격리
  - `db` 프로젝트는 테스트 파일을 한 번에 하나씩 실행한다(`fileParallelism: false`).
  - 각 테스트 전에 테이블을 비운다.
  - 단위 테스트(`unit` 프로젝트)는 DB에 접속하지 않아서, 함께 실행해도 서로 영향이 없다.

**클라이언트 IP 판단 [검증 필요]**

요청 제한은 `req.ip`로 IP를 구분한다. 프록시 뒤에서는 Express의 `trust proxy` 설정에 따라 `X-Forwarded-For`의 몇 번째 값을 쓸지가 정해진다. 이 값은 환경 변수 `TRUST_PROXY_HOPS`(기본 0)로 둔다.

조사 결과 (2026-10-19, 공식 문서·커뮤니티 기준. 실제 배포로 확인하지 않음)

- Render: 공식 문서를 찾지 못했다. 커뮤니티 글에 따르면 Render 프록시는 클라이언트가 보낸 `X-Forwarded-For`를 지우지 않고 자기 IP만 뒤에 붙이며, 앞단 프록시 개수(hop)에 대한 보고도 일정하지 않다.
- Vercel: 문서에 따르면 Vercel은 들어온 `X-Forwarded-For`를 덮어써 위조를 막는다. 다만 외부로 rewrite한 요청에 Render가 무엇을 받는지는 문서에 나와 있지 않다.

그래서 값을 추측으로 정하거나 바꾸지 않는다. 배포 후 **Vercel 경유**와 **Render 직접 접근** 두 경로에서 실제 헤더를 확인해 정한다. 절차: [docs/runbooks/auth-deploy-verification.md](../runbooks/auth-deploy-verification.md) 4단계

- 확인용 진단 코드는 임시 브랜치에서만 쓰고 `main`에 병합하지 않는다. 확인이 끝나면 제거한다.
- 진단은 IP 관련 값만 기록·응답한다: `req.ip`, 연결 주소, `X-Forwarded-For`, `X-Real-IP`, `X-Vercel-Forwarded-For`. 쿠키·`Authorization`·본문·쿼리, 그 밖의 헤더는 기록하지 않는다.
- 요청 제한 수치(위 표)는 MVP 초기값으로 유지한다.

알려진 위험

- Render 주소로 직접 요청하면 Vercel을 거칠 때보다 프록시가 하나 적다. 그래서 Vercel 경로에 맞춘 `TRUST_PROXY_HOPS`로는, 직접 요청한 사람이 `X-Forwarded-For`를 위조해 IP별 제한을 피할 수 있다.
- 반대로 값이 너무 작으면 모든 사용자가 같은 프록시 IP로 보여, 전체가 한도를 함께 쓰게 된다(정상 사용자가 429를 받는다).
- 따라서 배포 전에는 반드시 위 확인을 거친다. 계정 단위 제한(이메일별 로그인 시도 제한)은 필요하면 다음 작업으로 검토한다.

**Data API 접근 차단 [구현]** (`20261019070424_auth_data_api_lockdown`)

개발용 Supabase를 읽기 전용으로 점검한 결과(2026-10-19)는 다음과 같다.

- **권한(확인됨):**
  - `anon`·`authenticated`는 `public` 스키마 USAGE 권한이 있다.
  - `postgres` 역할의 기본 권한 때문에, Prisma가 `public`에 만드는 새 테이블·시퀀스에 이 두 역할의 모든 권한이 자동으로 붙는다.
- **자동 RLS(확인됨):**
  - `ensure_rls` 이벤트 트리거(`public.rls_auto_enable`)가 `public`의 새 테이블에 RLS를 켠다(ENABLE, FORCE 아님).
  - 다만 켜는 데 실패하면 로그만 남기고 계속 진행한다.
- **Data API 활성화 여부(확인됨: 꺼져 있음):** Data API가 켜져 있는지, 어떤 스키마를 노출하는지는 DB에서 확인할 수 없다(`authenticator` 역할에 `pgrst.db_schemas` 설정이 없음, 호스팅 플랫폼 설정에 있음).
  - 대시보드 **Project Settings → Data API**에서 꺼져 있는 것을 확인했다(2026-10-19, 이슈 #5).
  - 지금은 anon 키로 `public` 테이블에 접근하는 경로가 없다. DB 쪽 차단(RLS·권한 0)은 나중에 Data API를 켜는 경우를 대비한 것이다.
  - Data API를 켜려면, 먼저 노출할 스키마와 테이블별 권한·RLS 정책을 마이그레이션 PR로 정한다.

이번 마이그레이션이 하는 일:

1. 인증 테이블 4개에 RLS를 명시적으로 켠다. 정책이 없으므로 RLS를 적용받는 역할은 어떤 행도 읽거나 쓸 수 없다.
2. `anon`·`authenticated`의 인증 테이블 4개와 시퀀스 4개 권한을 모두 회수한다.
3. 마이그레이션을 실행하는 역할(Prisma 접속 역할, Supabase에서는 `postgres`)이 앞으로 `public`에 만드는 테이블·시퀀스에 이 두 역할의 권한이 자동으로 붙지 않게 기본 권한을 바꾼다.
4. 다음은 바꾸지 않는다: `supabase_admin` 등 다른 역할의 기본 권한, `auth`·`storage`·`realtime` 등 Supabase 시스템 스키마, `service_role` 권한.
5. `anon`·`authenticated` 역할이 없는 DB(로컬 PostgreSQL)에서는 2·3을 건너뛰고 RLS만 켠다.

- Express(Prisma)는 `postgres`(테이블 소유자, `BYPASSRLS`)로 접속하므로 영향을 받지 않는다.
- **보완 (`20261019074729_prisma_history_lockdown`):** 개발용 Supabase 적용 후 점검에서 `_prisma_migrations`에 `anon`·`authenticated`의 전체 권한이 남아 있는 것을 발견했다.
  - 원인: Prisma가 첫 마이그레이션보다 먼저 이 테이블을 만들기 때문에, 기본 권한을 바꾸기 전의 권한을 받는다.
  - 자동 RLS로 RLS는 켜져 있고 정책은 0개였다. 하지만 TRUNCATE 등은 RLS를 받지 않으므로 권한을 회수한다.
  - 새 DB에서도 같은 일이 생기므로, 마이그레이션으로 처리한다.
- 앞으로의 규칙 [확정]:
  - 새 테이블도 Data API로 열지 않는 것이 기본이다.
  - 프론트엔드가 Supabase 클라이언트로 직접 읽어야 하는 테이블이 생기면, 그 테이블에만 권한과 RLS 정책을 명시적으로 추가하는 마이그레이션을 PR로 만든다.
  - 새 테이블을 만드는 마이그레이션에도 `ENABLE ROW LEVEL SECURITY`를 함께 넣는다.
- 검증
  - 테스트 DB에 Supabase와 같은 역할과 기본 권한을 재현한 뒤 두 마이그레이션을 적용했다. RLS가 켜지고, 두 역할에 남은 권한이 0개이며, 새로 만든 테이블에도 권한이 붙지 않는 것을 DB 테스트로 확인했다.
  - 회수 구문이나 기본 권한 변경을 일부러 빼면 해당 테스트가 실패하는 것도 확인했다.
  - `anon`·`authenticated` 역할이 없는 PostgreSQL 17.11에서도 두 마이그레이션이 오류 없이 적용된다.

**PostgreSQL 버전 [확정]**

- 팀 개발용 Supabase DB는 PostgreSQL 17.11이다(2026-10-19 팀원 확인).
- 로컬 테스트 DB(`apps/api/docker-compose.test.yml`)와 CI(`.github/workflows/api-ci.yml`) 이미지를 모두 `postgres:17.11-alpine`으로 고정했다. 로컬 컨테이너에서 `server_version` 17.11을 확인했다.
- Supabase를 업그레이드하면 두 이미지 태그도 같이 바꾼다.
- [검증 필요] 실제 Supabase DB에 대한 연결과 마이그레이션 적용은 아직 하지 않았다. 버전이 같다는 것만 확인됐다.

**동작 [제안]**

- 대상은 항상 토큰의 회원 본인이다. 경로에 회원 ID를 받지 않으므로 다른 회원의 프로필을 고칠 수 없다.
- 프로필 행은 처음 저장할 때 만든다(upsert). 저장한 적이 없으면 조회는 빈 기본값을 돌려준다.
- 역할에 맞는 형식만 받는다(`strictObject`). 다른 역할의 항목이나 모르는 항목을 보내면 `400 VALIDATION_FAILED`다.
- 크리에이터 프로필의 `service_status`는 처음에 `DRAFT`다. 프로필 저장 요청은 이 값을 받지 않으므로, 저장만으로 공개되지 않는다(PROFILE-02).
- 의뢰인의 브랜드 정보는 모두 선택이다. 미입력을 이유로 다른 기능을 막지 않는다(P02).
- 주소는 `http://`·`https://`로 시작하고 올바른 URL이어야 한다(최대 2048자). `javascript:` 같은 주소는 거부한다.
- 관리자(`ADMIN`)는 프로필이 없으므로 `403 FORBIDDEN`이다.
- 이용 제한(`RESTRICTED`)·탈퇴(`WITHDRAWN`) 회원은 상태가 바뀌기 전에 받은 Access 토큰이 아직 만료 전이어도 조회·수정 모두 `403 FORBIDDEN`이다. 요청마다 DB에서 회원 상태를 다시 확인하기 때문이다(8장 Access 토큰 검증).
- 400·401·403이면 아무것도 저장하지 않는다. `name`과 프로필 항목은 한 트랜잭션에서 함께 저장된다.

**복수 선택 항목을 `text[]`로 바꾼 이유 [제안 · ERD v0.6과 다름]**

ERD v0.6은 콘텐츠 스타일·제작 역할을 `jsonb`로 적었다. 이 PR은 `text[]`(문자열 배열)로 저장한다.

두 방식 모두 DB CHECK 한 줄로 허용 값을 검사할 수 있다. 그래서 값 검증 가능 여부는 선택 이유가 아니다. (PostgreSQL 17.11 테스트 DB에서 2026-10-21에 확인)

| 방식     | 허용 값 CHECK                                                                           | 형태 검사                                                                               |
| -------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `text[]` | `content_styles <@ ARRAY['MODERN', ...]::text[]`                                        | 열 타입이 문자열 배열이라 따로 필요 없다                                                |
| `jsonb`  | `jsonb_typeof(content_styles) = 'array' AND content_styles <@ '["MODERN", ...]'::jsonb` | `jsonb_typeof`로 배열인지 확인해야 한다. 그러면 숫자·중첩 배열·객체도 `<@`에서 거부된다 |

- 두 방식 모두 같은 값을 두 번 넣는 것(`["MODERN", "MODERN"]`)은 이 CHECK로 막지 못한다. 중복은 API(`@kemi/shared`의 `uniqueList`)가 막는다.

`text[]`를 고른 이유는 다음과 같다.

1. **열 타입만으로 형태가 정해진다.** `text[]`에는 문자열 목록만 들어가므로 CHECK에는 허용 값만 적으면 된다. `jsonb`는 형태 검사(`jsonb_typeof`)를 함께 적어야 한다.
2. **서버 코드가 단순하다.** Prisma가 `text[]`를 `string[]`로 돌려준다. `jsonb`는 `JsonValue` 타입이라, 문자열 배열인지 확인하는 타입 가드를 거쳐야 한다(이 저장소는 타입 단언을 쓰지 않는다).
3. **다른 상태값과 같은 방식이다.** 6장의 "text + CHECK + shared 배열" 규칙을 그대로 따른다. CHECK 정의에 값이 `'MODERN'::text` 형태로 나오므로, status-check 테스트가 다른 상태값과 같은 방법으로 shared 배열과 비교한다.

- 기본값은 빈 배열이고 `NULL`은 CHECK로 막는다.
- 한계: 원소마다 추가 정보(예: 숙련도)를 붙여야 하면 `text[]`로는 부족하다. 그런 항목은 `skills`·`creator_skills`처럼 별도 테이블로 만든다. `jsonb`로 바꿔도 되지만 그때는 위 형태 검사를 다시 설계해야 한다.
- 검색: "이 스타일을 가진 크리에이터"는 `content_styles @> ARRAY['BRIGHT']`로 찾을 수 있고, 필요하면 GIN 인덱스를 추가한다. `jsonb`도 `@>`와 GIN 인덱스를 지원하므로 이 점은 차이가 없다.

**그 밖의 ERD v0.6과 다른 점 [제안]**

- 프로필 PK는 `user_id`다(회원당 프로필 1개).
- 마이그레이션 `20261021005250_role_profiles`에 두 테이블의 RLS를 함께 켰다(8장 Data API 규칙).

**팀 공용 DB 적용 범위 (리뷰·병합 후, 아직 적용하지 않음)**

PR #13이 리뷰·병합된 뒤, 이슈에 아래 범위를 공유하고 동의를 받은 다음 적용한다. 순서는 8장 절차와 같다.

- 적용할 마이그레이션: `20261021005250_role_profiles` 하나
- 바뀌는 것 (새로 만드는 것뿐)
  - 테이블 2개: `client_profiles`, `creator_profiles` (행 없음)
  - FK 2개: `user_id` → `users.id` (`ON DELETE RESTRICT`)
  - CHECK 5개: `client_profiles_industry_check`, `creator_profiles_niche_check`, `creator_profiles_content_styles_check`, `creator_profiles_production_roles_check`, `creator_profiles_service_status_check`
  - RLS 켜기 2개 (정책 없음)
- 바뀌지 않는 것: 기존 4개 테이블의 구조·데이터, 기존 마이그레이션 3개와 이력, 역할·기본 권한 설정
  - FK를 만들 때 `users`에 잠깐 잠금이 걸린다. 새 테이블이 비어 있어 바로 끝난다.
- 적용 전 읽기 전용 점검(`BEGIN READ ONLY`)
  - 적용된 마이그레이션이 3개이고 모두 완료 상태
  - 두 테이블이 아직 없음
  - `postgres`의 public 기본 권한에 `anon`·`authenticated`가 없음
- 적용: `prisma migrate deploy` (`MIGRATION_DATABASE_URL` = Session pooler)
- 적용 후 확인
  - 마이그레이션 4개 완료
  - 두 테이블의 RLS 켜짐, CHECK 5개 존재
  - `anon`·`authenticated`의 두 테이블 권한 0개 (MAINTAIN 포함)
  - `/health/ready` 200
- 예상과 다르면 멈추고 보고한다. 되돌리기 SQL(두 테이블 삭제 + 이력 행 삭제)은 행이 없을 때만 쓰는 수동 비상 절차이며, 실행 전에 다시 공유한다.

**검증**

- 테스트 DB에서 마이그레이션 적용과 프로필 DB 테스트 85개 통과
  - 기본값, 부분 수정
  - PATCH 값 규칙 표: 항목 14개마다 보내지 않음·빈 문자열·공백만·`null`의 결과 (56개)
  - 잘못된 주소·값, 중복 선택, 모르는 항목은 400
  - 공개 상태 유지, 이름 변경, 잘못된 이름이면 전체 미저장
  - 401, 관리자 403
  - 의뢰인·크리에이터가 각각 제한·탈퇴되면 기존 토큰으로 조회·수정 403, 저장된 값 유지
  - CHECK가 직접 쓰기를 거부
- 엄격 검사·빈 값 변환·관리자 차단·이름 저장·주소 형식 검사·RLS·인증의 회원 상태 확인을 일부러 빼면 해당 테스트가 실패하는 것을 확인했다.
- [검증 필요] 팀 공용 Supabase 적용 (위 범위)

## 11. 소셜 로그인 (Google·카카오)

1장(이메일과 소셜 계정)과 5장(쿠키·OAuth)의 확정·제안 사항을 구현한다. DB 구조는 바꾸지 않는다(`auth_identities`는 첫 마이그레이션에 있다).

> **[미검증] 실제 Google·카카오 로그인은 아직 한 번도 확인하지 않았다.** 제공자 앱·키·콜백 주소가 없어 가짜 제공자로만 테스트했다. 팀원이 준비할 항목은 [소셜 로그인 연동 문서](../handoff/2026-10-21-social-login.md)의 "팀원 준비 목록"에 있다.

**범위**

- 포함: Google·카카오 로그인 시작·콜백, 처음 온 소셜 계정의 역할·표시 이름 입력 후 가입, 기존 소셜 계정 로그인
- 제외: 기존 회원에 소셜 계정 연결(1장: MVP 제외), 소셜 계정 연결 해제, 제공자 토큰 보관(로그인 확인에만 쓰고 저장하지 않는다)

**흐름 [제안]**

1. 프론트엔드가 브라우저를 `GET /api/auth/{provider}/start`로 이동시킨다(fetch가 아님).
2. 서버는 `state`(CSRF 방지)와 PKCE `code_verifier`를 만들어 서명한 JWT로 `kemi_oauth_state` 쿠키(10분)에 담고, 제공자 동의 화면으로 302 이동한다.
3. 제공자가 `{APP_ORIGIN}/api/auth/{provider}/callback`으로 돌려보낸다. 서버는 쿠키를 지우고 다음을 확인한다.
   - 쿠키 서명·만료·용도가 맞고, 쿠키의 제공자와 경로의 제공자가 같고, 쿼리 `state`가 쿠키 값과 같다. 아니면 제공자에 코드를 보내지 않고 `SOCIAL_FAILED`다.
   - `error=access_denied`면 `SOCIAL_CANCELLED`다.
4. 서버가 코드를 제공자 토큰으로 바꾸고 회원 정보를 받는다. `(provider, provider_user_id)`로 소셜 계정을 찾는다.
   - **있음**: 회원 상태가 `ACTIVE`면 로그인 세션을 만들고 Refresh 쿠키를 설정한 뒤 프론트엔드 `/auth/social/callback?result=login`으로 보낸다. Access 토큰은 주소에 싣지 않는다. 프론트엔드가 `POST /api/auth/refresh`로 받는다. 이용 제한·탈퇴 회원이면 `error=FORBIDDEN`이고 세션을 만들지 않는다.
   - **없음**: 아직 회원을 만들지 않는다. 제공자 회원 정보를 서명한 가입 티켓 쿠키(`kemi_social_signup`, 10분)에 담아 `?result=signup`으로 보낸다.
5. 프론트엔드는 `GET /api/auth/social/signup`으로 이름 후보를 받아 가입 화면을 보여주고, 사용자가 확인한 역할·표시 이름을 `POST /api/auth/social/signup`으로 보낸다(`Origin` 검사). 서버는 회원과 소셜 계정을 한 번에 만들고 회원가입과 같은 응답을 준다.

- 결과는 항상 `APP_ORIGIN`의 고정 경로 `/auth/social/callback`으로만 보낸다. 요청에서 받은 주소로 보내지 않는다(오픈 리다이렉트 방지).
- 중간 단계 값은 DB에 저장하지 않는다. `JWT_ACCESS_SECRET`으로 서명하되 `audience`(`kemi:oauth-state`, `kemi:social-signup`)로 용도를 나눠, Access 토큰·state 쿠키·가입 티켓을 서로 바꿔 쓸 수 없게 한다.
- 두 쿠키 모두 `HttpOnly; Secure; SameSite=Lax; Path=/api/auth`다. 제공자에서 돌아오는 요청은 최상위 GET 이동이라 `Lax` 쿠키가 실린다.

**계정 규칙 [확정 · 1장]**

- 같은 이메일이라는 이유로 기존 회원과 병합하지 않는다. 같은 이메일의 이메일 회원이 있어도 소셜 가입은 별도 회원이 된다.
- 소셜 가입 회원은 `users.email`·`password_hash`가 `NULL`이다. 이메일·비밀번호 로그인을 할 수 없다.
- 제공자 이메일은 `auth_identities.provider_email`에만 저장하며, 제공자가 확인한 이메일만 저장한다.
  - Google: `email_verified`가 `true`일 때
  - 카카오: `is_email_valid`와 `is_email_verified`가 모두 `true`일 때

**가입 티켓(신규 가입용 임시 인증 정보)의 수명 [제안]**

| 항목      | 동작                                                                                                                                                                                                                                |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 만료      | 발급 후 10분(JWT `exp`, 쿠키 `Max-Age=600`). 지나면 조회·가입 모두 `401 UNAUTHENTICATED`이고 회원을 만들지 않는다. state 쿠키도 같은 10분이며, 지나면 제공자에 코드를 보내지 않고 `SOCIAL_FAILED`다                                 |
| 일회성    | 가입에 성공하면 쿠키를 지운다. 쿠키 값을 다시 보내도 같은 `(provider, provider_user_id)`가 이미 있어 `409 CONFLICT`다. 회원은 삭제하지 않으므로(탈퇴도 상태만 바뀜) 한 번 쓴 티켓으로 다시 가입할 수 없다                           |
| 동시 사용 | 같은 티켓으로 동시에 가입하면 회원·소셜 계정 생성이 한 트랜잭션이고, 두 번째 요청은 UNIQUE 인덱스에서 첫 번째 커밋을 기다린 뒤 실패해 통째로 되돌려진다. 결과는 `201` 하나와 나머지 `409`이고 회원·소셜 계정·세션은 하나씩만 남는다 |

- 티켓은 서버에 저장하지 않는 서명 토큰이라, "사용됨" 표시를 따로 두지 않고 DB의 UNIQUE 제약으로 한 번만 쓰이게 한다. 가입 전 조회(`GET /api/auth/social/signup`)는 읽기만 하므로 만료 전까지 여러 번 불러도 된다.
- state 쿠키의 일회성은 콜백에서 쿠키를 지우는 것과 10분 만료로 지킨다. 제공자의 인가 코드도 제공자 쪽에서 한 번만 쓸 수 있다.

**제공자별 차이 [검증 필요]**

| 항목      | Google                                     | 카카오                                                             |
| --------- | ------------------------------------------ | ------------------------------------------------------------------ |
| 동의 화면 | `accounts.google.com/o/oauth2/v2/auth`     | `kauth.kakao.com/oauth/authorize`                                  |
| 토큰 교환 | `oauth2.googleapis.com/token`              | `kauth.kakao.com/oauth/token`                                      |
| 회원 정보 | `openidconnect.googleapis.com/v1/userinfo` | `kapi.kakao.com/v2/user/me`                                        |
| 식별 값   | `sub`                                      | `id` (숫자 → 문자열로 저장)                                        |
| PKCE      | 사용 (`S256`)                              | 사용 안 함. 카카오 REST API 문서에 PKCE 항목이 없어 `state`만 쓴다 |
| 비밀 값   | Client Secret 필수                         | Client Secret: 카카오 앱에서 기본 사용. 끈 앱이면 보내지 않는다    |

- 위 주소·필드는 2026-10-21 공식 문서 기준이다.
- 카카오 응답 필드는 카카오 개발자 문서 "사용자 정보 조회"(한국어 REST API 문서) 원문과 대조했다(2026-10-21).
  - `id`: `Long`, 회원번호, 필수
  - `kakao_account.email`: 대표 이메일 (선택, 동의항목 "카카오계정(이메일)")
  - `kakao_account.is_email_valid`: `false`면 이메일이 다른 카카오계정에 사용돼 만료된 것
  - `kakao_account.is_email_verified`: 인증된 이메일 여부
  - `kakao_account.profile.nickname`: 닉네임 (선택, 동의항목 "닉네임" 또는 "프로필 정보")
  - 요청: `GET`, `Authorization: Bearer ${ACCESS_TOKEN}`, `Content-Type: application/x-www-form-urlencoded;charset=utf-8`(문서상 필수라 함께 보낸다)
  - 토큰 요청 본문은 `grant_type`, `client_id`, `redirect_uri`, `code`, `client_secret`뿐이고 `code_verifier`·PKCE 항목은 없다.
- [미검증] 실제 응답은 키를 받은 뒤 확인한다. 동의항목을 켜지 않으면 이메일·닉네임이 오지 않으며, 이때도 가입은 된다(이름은 사용자가 입력).
- 회원 정보 응답이 예상 형식과 다르면 `SOCIAL_FAILED`로 처리한다. 제공자 응답 내용은 기록하지 않는다(토큰이 들어 있을 수 있음).

**설정**

- 환경 변수: `GOOGLE_CLIENT_ID`·`GOOGLE_CLIENT_SECRET`(둘 다), `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`(선택). 없는 제공자는 `error=SOCIAL_UNAVAILABLE`로 안내하며, 서버는 키 없이도 시작된다.
- 제공자 콘솔에 등록할 콜백 주소
  - 로컬: `http://localhost:5173/api/auth/{google|kakao}/callback` (Vite 프록시)
  - 배포: `https://<Vercel 도메인>/api/auth/{google|kakao}/callback` (Vercel rewrite)
- [미검증] 실제 키·콜백 주소 등록이 아직 없다. 팀원 준비 목록(연동 문서)을 마친 뒤 로컬과 배포 환경에서 성공·취소·재로그인·탈퇴 회원 차단을 확인한다.

**검증**

- 제공자 어댑터 단위 테스트 9개: 동의 화면 주소, 토큰 교환 요청 내용, 확인된 이메일만 저장, 응답 형식 오류
- 가짜 제공자로 DB 테스트 26개
  - state 불일치·쿠키 없음·위조·다른 제공자 쿠키·만료, 취소, 통신 실패
  - 가입 티켓: 10분 만료, 만료 티켓 401, 재사용 409, 동시 가입 3건 중 1건만 성공, 탈퇴 후에도 재사용 불가
  - 처음 온 계정은 가입 전까지 회원을 만들지 않음, 가입 후 같은 계정 재로그인
  - 같은 이메일 자동 병합 없음, 이용 제한 회원 차단
  - 티켓 없음 401, 다른 Origin 403, ADMIN 400, 티켓 재사용 409, 용도가 다른 토큰 거부
- state 비교, 제공자 일치, 회원 상태 확인, `audience` 검사, `Origin` 검사, Google 이메일 확인 여부, 만료 검사(1시간 허용 오차), 티켓 유효 시간, 중복 가입 409 처리를 일부러 바꾸면 해당 테스트가 실패하는 것을 확인했다. 바꾼 코드는 모두 되돌렸고 최종 diff에 남지 않았음을 확인했다.
