# 3-C 테스트 결제·결과 확인·재조회

- `frontend-plan.md` §3단계·S11, `frontend-feature-matrix.md` PAY-01/02, `기술 스택.pdf`와 현재 Workspaces 구성을 따른다. 기존 React Router·Query·Axios·Zod·공통 Dialog/Button·KEMI 토큰을 재사용하며 의존성을 추가하지 않는다.
- `api문서.txt`와 현재 API/shared 코드에 결제/주문/PG 승인·조회 계약이 없다. 실제 제품 endpoint/DTO·Toss SDK·키를 추정하지 않는다. **DEV/MSW `/__mock__/payments/:contractId`에서만 실행하는 PG 대역이며 Toss Sandbox 연동 완료가 아니다.** 운영에는 연결 준비 안내만 제공한다.

## 흐름과 불변 조건

1. 3-B의 동일 버전 양측 서명으로 생성한 계약만 조회한다. 서명 저장본의 금액·버전·당사자를 참조하며 URL/브라우저 금액을 받지 않는다. 의뢰인은 주문/검증, 양 당사자는 내역 조회만 가능하다.
2. `create`에 주문 ID를 포함한다. 준비/결과 불명확/성공 주문이 있으면 새 ID를 차단하고, 같은 ID 재전송은 기존 주문을 반환한다. 확정 실패/취소 후에만 별도 확인창에서 새 주문을 만든다. 이전 주문 이력은 보존한다.
3. 확인창의 `verify`는 개발용 PG 결과 시연이다. 서버 대역이 주문·계약 전액·KRW를 대조한다. READY에서 한 번 처리하고 재전송으로 재승인하지 않는다. 성공/실패/취소는 이 Mock의 종결 상태다. 불명확은 실패로 취급하지 않는다.
4. `/payments/result`의 `success`, `amount`, `paymentKey`를 승인 증거로 사용하지 않는다. 계약/주문 식별로 기존 상태만 조회한다. 주문 없는 계약 진입은 최신 주문·이력을 보여주고 잘못된 주문 식별은 오류다.
5. 응답 유실/네트워크/형식 오류는 새 주문을 잠그고 동일 명령 재시도·기존 결제 재조회를 제공한다. 재전송 ID는 유지한다. 결과 불명확 주문은 재결제 버튼 없이 조회만 제공하며 `settled` 시나리오가 지연된 모의 제공자 결과를 조회 시 반영한다.
6. bearer·ACTIVE·역할/당사자·계약을 검사하고 지연 후 session epoch/당사자/계약을 다시 확인한다. 화면도 epoch 변경 후 응답을 버리고 조회 취소/개인 캐시 제거는 기존 세션을 따른다. Query/Mutation 자동 재시도·재접속 자동 조회는 하지 않는다.
7. PG 이벤트 revision은 중복/과거 응답을 무시하며 성공을 늦은 실패로 되돌리지 않는다. 실제 webhook/DB 원자성 증거가 아닌 모델 검사다. 결제 성공으로 제작/납기/정산을 시작하지 않는다.

## 미결정·실제 연동에 필요한 계약

- 주문 생성·멱등 키 수명/범위, 계약별 활성 주문 제약과 PG 승인/조회 DTO·오류·조회 권한, 브라우저 복귀 식별/refresh 복원, webhook 서명/중복·순서·동시 조회/승인 원자성, 만료/취소와 늦은 승인 충돌을 API팀과 조율해야 한다.
- D08 및 D10~D12 등 계약 변경·금액/VAT/절사·취소/환불 정책은 기존 미결정 그대로다. 이번에는 이미 서명한 양의 정수 금액 전체를 Mock에서 사용하며 세금/수수료 계산을 만들지 않는다. Mock의 READY/UNKNOWN/종결 상태·revision·이벤트 시연은 실제 PG 상태 계약을 대신하지 않는다.
- 단일 탭 메모리라 새로고침 시 계약/주문이 초기화된다. 다시 로그인해도 없는 계약은 실패 안내하며 성공으로 복원하지 않는다. 실제 API/DB·영구 저장/다중 탭·Toss Sandbox 결제창/승인/조회·알림·외부 제공자는 미연결/미검증이다.
- 공개 제안 경로의 조건→양측 서명→계약→Mock 결제 통합까지만 다룬다. 직접 의뢰 경로 통합은 6단계, 준비/제작은 4단계 범위다. **3-C 클라이언트/Mock과 3단계 전체 완료를 구분한다.** 실제 Sandbox·계약 조율이 남아 단계 전체 완료가 아니다.
